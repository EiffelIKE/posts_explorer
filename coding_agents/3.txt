  What's in src/api/
  - schemas.ts (src/api/schemas.ts): Zod schemas for users and posts. The User,
    Post and NewPost types are now generated from them; types.ts (src/types.ts)
    just re-exports them, so existing imports still work.
  - client.ts (src/api/client.ts): a request() helper. It throws an ApiError
    (with the HTTP status) when a response isn't 2xx, and checks every response
    body against its schema.
  - endpoints.ts (src/api/endpoints.ts): fetchUsers, fetchUserPosts and
    createPost. As you asked, fetchUsers() has no search parameter and there's
    no debounce. Step 4 will filter the cached list with the existing
    filterByName.
  - queries.ts (src/api/queries.ts):
    - createQueryClient(): data is fetched once per session and never refetched
      (staleTime: Infinity, since JSONPlaceholder data never changes), with one
      retry so errors show quickly.
    - Hooks: useUsers, useUser(id) (picks one user out of the cached list, no
      extra request), useUserPosts, useLocalPosts and useCreatePost.
  - localIds.ts (src/api/localIds.ts): moved here from src/posts/, with its
    import updated.
  - src/test/handlers.ts: MSW now has default handlers for all three endpoints.
    The POST handler mimics JSONPlaceholder and always returns id: 101.

  One change from the plan: created posts don't go into the server posts list.
  They get their own cache entry and the UI shows them above the server posts.
  Putting them in the server list breaks in two cases:
  - While the list is still loading, the incoming fetch overwrites the new post.
  - After the list has failed to load, adding the post marks the query as
    successful, so the error disappears and the real posts never load. That
    conflicts with the "you can still write a new post" message in the error
    state.

  I logged this as decision 12 in PLAN.md, with client-side search (13) and the
  API layer layout (14), and ticked step 3.
